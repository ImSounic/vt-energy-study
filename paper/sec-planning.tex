\subsection{Goals and Research Questions}\label{sec:planning-goals}
We reviewed the A1 goals; the general goal follows the template of Basili et al.~\cite{basili1994gqm}:

\begin{list}{}{\setlength{\leftmargin}{1em}\setlength{\rightmargin}{0pt}\setlength{\topsep}{2pt}}\item[]
\emergencystretch=1.5em
\textbf{Analyze} Java thread management constructs (sequential baseline, platform threads, fixed thread pools, Fork/Join, virtual threads) \textbf{for the purpose of} characterizing \textbf{with respect to} energy consumption and its relationship to execution time \textbf{from the point of view of} Java developers \textbf{in the context of} heterogeneous (P/E) multicore processors.
\end{list}

\noindent We refer to the five constructs as sequential execution (SEQ), one platform thread per task (PT), the fixed thread pool (FP), Fork/Join (FJ), and virtual threads (VT); Table~\ref{tab:variables} defines each. Three specific goals share the viewpoint and context of the general goal.

\emph{G1: concurrency level}, to evaluate whether the 2014 energy-concurrency relationship~\cite{pinto2014energy} still holds under DVFS-managed hybrid processors.
\begin{planrq}
\item[RQ1.1] How does energy/op vary with the concurrency level, per construct and workload?
\item[RQ1.2] Is sequential execution the lowest-energy option?
\item[RQ1.3] Is lower execution time associated with lower energy/op across configurations (``faster${}={}$greener'')?
\end{planrq}

\emph{G2: virtual threads}, to compare them with the platform-thread-based constructs on CPU-bound, blocking, and network-I/O workloads.
\begin{planrq}
\item[RQ2.1] How does VT energy/op compare with each other construct, per workload?
\item[RQ2.2] At which concurrency levels, if any, does VT have the lowest energy/op?
\end{planrq}

\emph{G3: restriction to efficiency cores}, to evaluate the energy cost of asymmetry-unaware scheduling: the Intel arm carries the asymmetry claim through equal-count pinning, and the Mac arm measures QoS confinement.
\begin{planrq}
\item[RQ3.1] Does restricting execution to E cores change energy/op, and at what time cost?
\item[RQ3.2] How is CPU energy split between the P and E clusters under default scheduling, and does the split differ between constructs?
\end{planrq}

Compared with A1, SEQ is now a treatment (RQ1.2), RQ1.3 is new, and G3 is split by platform because macOS has no CPU affinity: the Mac restricts execution through the quality-of-service (QoS) class and uniquely yields the per-cluster split of RQ3.2.

\subsection{Hypotheses}\label{sec:planning-hypotheses}
Table~\ref{tab:hypotheses} gives a main pair and one pair per RQ. All H0s are tested on CPU-cluster energy/op on the Mac and package energy/op on Intel. On SLEEP and SOCKET the primary tested measure is idle-subtracted energy/op with the detection-limit rule of Section~\ref{sec:planning-analysis}, and H0-1.3 is tested on CPU only, because on blocking workloads energy/op equals idle power times time/op by construction (both pilots, Section~\ref{sec:meas-pitfalls}). The SLEEP and SOCKET tests of H0-1.1, H0-2.1, and H0-2.2 are repeated on memory-subsystem energy (DRAM${}+{}$AMCC${}+{}$DCS) as a separate Holm-corrected family on the Mac only: the Intel 255H exposes no DRAM RAPL domain, and its uncore domain is not equivalent.

\subsection{Experimental Units and Workloads}\label{sec:planning-units}
The experimental units are three benchmark kernels, each running 256 independent tasks per operation so that total work is identical at every $p$. \emph{CPU} computes a 128$\times$128 Mandelbrot set (at most 500 iterations per point) from the 2014 benchmark set~\cite{pinto2014energy}, tying G1 to that baseline; it is deterministic and allocation-free, each task computes the full grid offset by its task index (so tasks are near-identical), and it stands for embarrassingly parallel compute such as image or batch processing. \emph{SLEEP} runs a 10\,ms \texttt{Thread.sleep} per task, isolating the unmount-on-block mechanism of VT~\cite{jep444} with a nominally controlled latency (calibrated by ancillary experiment AX5, Section~\ref{sec:threats}); it stands for a request handler waiting on a remote call. \emph{SOCKET} (new) adds network I/O: each task opens a loopback TCP connection to an out-of-process server, sends 64\,B, and receives a 64\,B reply; it stands for a service fan-out over the network. The server is a single-threaded Java NIO server that schedules each reply 10\,ms after the request on a timer, so it blocks no thread; its energy share is measured in a server-only run and reported as a constant per-task overhead. One connection per task keeps the I/O pattern identical across constructs.

\emph{Randomization.} The units are fixed, purposively chosen kernels, so randomization applies to run order: one recorded, seeded shuffle at fork level, which spreads residual drift and breaks the run-order confound of the A1 Intel pilot (Section~\ref{sec:meas-pitfalls}).

\subsection{Variables}\label{sec:planning-variables}
Table~\ref{tab:variables} lists the variables. SEQ and PT have no $p$, which avoids duplicate cells. The top level, $p = 256$, equals the task count: a pool can then overlap all 256 waits, as PT and VT do. On the blocking workloads (SLEEP, SOCKET), a bounded pool's time/op has an analytic floor of $\lceil 256/p \rceil \times d$, with $d$ the measured per-task wait (AX5) and SEQ as the $p = 1$ case, so FP and FJ being slower than VT at $p < 256$ is known by construction, not a finding.

\subsection{Design}\label{sec:planning-design}
The design is within-subjects: every unit receives every treatment, so the workload is a blocking factor. \emph{Experiment~1} (RQ1.1 to RQ2.2) is a full factorial of construct $\times$ $p$ $\times$ workload under DEFAULT QoS: SEQ and PT give one cell each and FP, FJ, and VT seven each, so 23 cells per workload and 69 in total. \emph{Experiment~2} (RQ3.1) runs BACKGROUND QoS at $p \in \{4, 16\}$, which bracket the six E cores: 8 cells per workload, 24 in total; their DEFAULT counterparts come from Experiment~1, whose cluster split also answers RQ3.2.

One fork, a fresh JVM run, is one trial~\cite{georges2007rigorous}; its value is the median of its 5 measured iterations. With 10 forks per cell, $(69 + 24) \times 10 = 930$ runs execute in one randomized schedule, in batches of about 40 (Section~\ref{sec:measurement}). The pilots (Table~\ref{tab:pilot}) support $n = 10$: the fork-to-fork coefficient of variation (CV) of CPU-bound energy/op was below 1\% on the Mac and 0.1 to 0.6\% on Intel, so 10 forks detect differences far below 10\%. On SLEEP, Mac CPU energy/op was at the noise floor (CV up to 116\%), whereas memory-subsystem energy/op had a CV of 1.4\% (FP), 2.9\% (FJ), 1.3\% (VT), and 9.1\% (PT). The Intel arm runs the Experiment~1 cells plus an equal-count placement arm (2P, 2E, and 2LP-E for the 8 Experiment-2 cells per workload, 72 cells) at 5 forks per cell: 705 runs, about 13\,h including heat-soak (Section~\ref{sec:meas-procedure}), within the 15\,h allowance.

Per cell we report the median, interquartile range, and CV, and plot $\Lambda$ curves (energy/op against $p$), energy-versus-time scatter plots, and cluster-split bars. All tests are non-parametric, an a priori choice for samples of 10 forks of unknown distribution, at $\alpha = 0.05$ with Holm correction within each family of Table~\ref{tab:families}; effect sizes are Cliff's~$\delta$ and $\varepsilon^2$ with bootstrap confidence intervals (CIs).

\begin{planitems}
\item[\textbf{Main.}] Per workload, Kruskal-Wallis across SEQ, PT, $\mathrm{FP}_8$, $\mathrm{FJ}_8$, and $\mathrm{VT}_8$ on CPU ($p = 8$ is near the Mac's 10 cores; on Intel $p = 16$, its core count, replaces $p = 8$) and, at equal concurrency, across PT, $\mathrm{FP}_{256}$, $\mathrm{FJ}_{256}$, and $\mathrm{VT}_{256}$ on SLEEP and SOCKET (SEQ, the $p = 1$ floor case, is excluded); H0 is rejected if any workload's test rejects.
\item[\textbf{H0-1.1.}] Kruskal-Wallis across $p$ for FP, FJ, and VT per workload; Dunn post-hoc tests; $\varepsilon^2$.
\item[\textbf{H0-1.2.}] A split sample per workload avoids selection bias: forks 1 to 5 select the lowest-median concurrent configuration and forks 6 to 10 test SEQ against it (Mann-Whitney~$U$, Cliff's~$\delta$); forks are assigned by fork index, fixed before any data exist, not by schedule position.
\item[\textbf{H0-1.3.}] Spearman~$\rho$ between cell-median time/op and energy/op on CPU (23 cells).
\item[\textbf{H0-2.1.}] Per workload and $p$, Kruskal-Wallis across FP, FJ, VT, PT, and SEQ (PT and SEQ enter at every $p$); Dunn tests of VT against each; Cliff's~$\delta$.
\item[\textbf{H0-2.2.}] Intersection-union (IU) test: rejected only if $\mathrm{VT}_p$ is significantly lower than every alternative (one-sided Mann-Whitney~$U$); we report the smallest such $p$, with~$\delta$.
\item[\textbf{Blocking.}] On SLEEP and SOCKET the decisive H0-2.1 contrasts are VT against PT (equal concurrency, so only OS versus virtual threads differ) and against $\mathrm{FP}_{256}$ and $\mathrm{FJ}_{256}$; H0-2.2 is tested only at $p = 256$, and FP and FJ at $p < 256$ are reported as floor ratios (Section~\ref{sec:planning-variables}).
\item[\textbf{H0-3.1.}] Mann-Whitney~$U$ of DEFAULT against BACKGROUND per cell; Cliff's~$\delta$; time penalty (\%) with a bootstrap 95\% CI. On Intel, 2E and 2LP-E are compared with 2P (equal count); unpinned runs are reported descriptively.
\item[\textbf{H0-3.2.}] Per workload at $p \in \{4, 16\}$ under DEFAULT QoS, Kruskal-Wallis of the E-cluster share across the five constructs.
\end{planitems}

A non-rejection is not read as equivalence: two one-sided tests (TOST) claim equivalence when the bootstrap 90\% CI of the ratio of medians lies within $[0.95, 1.05]$; we treat a 5\% difference in energy/op as the smallest effect of practical interest to a developer, and the margin also exceeds twice the instrument's boundary staleness (Section~\ref{sec:meas-energy}). Equivalence should be near-automatic on CPU-bound cells with a CV below 1\% and unlikely in the memory family, where PT's CV was 9.1\%. Idle-subtracted values whose bootstrap CI includes zero are reported as below the detection limit. \emph{Power check.} After the second pilot, for VT against PT per workload, SEQ against the best concurrent configuration on CPU, and VT against PT in the memory family, the pilot CV gives the power at $n = 10$ for a 10\% difference; if it is below 0.8, forks are added to that comparison, up to 15. The analysis uses Python (pandas, SciPy, scikit-posthocs).
